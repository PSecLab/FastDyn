# BoardRunner: Full Rehosting Flow

This document walks through the complete BoardRunner workflow from a raw firmware binary to a verified, fully emulated peripheral model — without access to physical hardware after the initial trace collection step.

---

## What is BoardRunner?

**BoardRunner** is an automatic firmware rehosting framework. Given a firmware binary and one initial run against real hardware, it automatically learns how each peripheral behaves and synthesizes a high-fidelity software model of it. The resulting setup lets you run, fuzz, and analyze the firmware entirely in software with no board attached.

BoardRunner sits at the top of a two-layer stack:

```
┌──────────────────────────────────┐
│           BoardRunner            │  ← rehosting framework (this repo)
│  Learner · Verifier · VIO Models │    learns peripherals, manages models
├──────────────────────────────────┤
│             FastDyn              │  ← emulation engine (QEMU plugin)
│   Elder · Passthrough · Classic  │    executes firmware, intercepts MMIO
└──────────────────────────────────┘
```

**FastDyn** is the underlying emulation engine. It is a QEMU plugin that intercepts all memory-mapped I/O (MMIO) accesses performed by the firmware and routes them to device model backends. FastDyn is not a QEMU fork — it works with upstream QEMU through the plugin API. The backends are:

| Backend | What it does |
|---------|-------------|
| `elder` | Runs a dynamically loaded `.so` model generated by BoardRunner-Learner |
| `passthrough` | Forwards MMIO directly to real hardware via LibHW (ST-Link / J-Link) |
| `classic` | Built-in hand-written core models (timers, NVIC, etc.) |
| `twintrace` | Records or replays MMIO traces for deterministic re-execution |

BoardRunner adds the automation layer on top: it learns the model, verifies it, and iteratively corrects it using an LLM.

## Architecture Overview

```
Firmware binary + Platform config (.toml)
          │
          ▼
    ┌─────────────┐  passthrough   ┌──────────┐
    │   FastDyn   │ ─────────────► │  LibHW   │ ──► Physical board (ST-Link)
    │  (QEMU plugin)│              └──────────┘
    └──────┬──────┘
           │ I/O trace (hardware_log/io.log)
           ▼
    ┌──────────────────────────────────┐
    │      BoardRunner-Learner         │
    │                                  │
    │  Encoder ──► LLM (CodeGen) ──► C model (.c)
    │                                  │
    │  Verifier ──► RCA ──► revised_prompt.txt
    └──────────────────────────────────┘
           │ compiled .so
           ▼
    FastDyn elder backend  (no board needed)
```

**BoardRunner-Learner** has three components:

- **Encoder** — Converts raw MMIO traces into a compact timed automaton. It separates the initialization sequence from steady-state repeating behavior, annotates each register with its symbolic name (from the SVD file), computes Shannon entropy per register to identify data-bearing vs. control registers, and detects interrupt handlers.

- **CodeGen** — Feeds the encoded automaton to an LLM (GPT-5 Thinking / Gemini 2.5 Pro). The LLM selects the appropriate FastDyn VIO APIs and synthesizes a C device model. The model is automatically compiled and evaluated.

- **Verifier** — Replays the original I/O trace through the synthesized model and diffs the responses against the hardware ground truth. If mismatches are found, the Root Cause Analysis (RCA) module locates the broken pattern, classifies the error, and produces a correction prompt that is fed back to CodeGen.

## The Full Workflow (Step by Step)

### Prerequisites

- A NUCLEO board connected via ST-Link (only needed for Step 0)
- FastDyn built: `build/libfastdyn.so`
- BoardRunner SDK built: `boardrunner/boardrunner_sdk/build/`
- An OpenAI or Google Gemini API key set in the environment

---

### Step 0 — Collect the hardware I/O trace (HITL)

Run the firmware in passthrough mode. FastDyn intercepts every MMIO access and logs it, while LibHW forwards the actual read/write to the physical peripheral on the board. This produces the ground-truth trace.

```bash
fastdyn run -c <config.toml>
```

Output: `hardware_log/io.log`

This is the only step that requires physical hardware. All subsequent steps work entirely in software.

> For DMA-intensive firmware (ADC+DMA, Ethernet), BoardRunner uses **Synchronized Memory** to keep the emulated RAM and hardware RAM coherent during passthrough, ensuring DMA transfers are captured correctly.

---

### Step 1 — Encode the trace and generate an LLM prompt

The Encoder processes `io.log` for each peripheral group you want to model. It produces a compact automaton and writes a structured prompt to a work directory.

```bash
fastdyn generate \
  -hw hardware_log/io.log \
  -b <platform>          \   # e.g. STM32H753x
  -p <PERIPH1> [-p <PERIPH2> ...] \   # peripheral names to include in the trace context
  -mname "<ModelName>"   \   # logical name for this model
  -ms "<PERIPH1>" [-ms "<PERIPH2>" ...] \  # peripherals this model is responsible for
  -o ./fastdyn_work_<name>
```

**`-p` vs `-ms`:** `-p` selects which peripherals' trace accesses are included in the prompt context (useful when peripherals are interdependent). `-ms` selects which peripherals this particular model will handle at runtime.

Run once per compositional model you want to generate.

---

### Step 2 — Synthesize and compile the model (LLM)

Send the encoded prompt to the LLM. BoardRunner-Learner CodeGen receives the response, extracts the C model, writes it to the output path, and compiles it to a `.so` shared library.

```bash
fastdyn llm \
  -d fastdyn_work_<name>          \   # work directory from Step 1
  -o path/to/generated/model.c    \   # output C file (can specify multiple -o for compositional models)
  --compile                        \   # compile after generation
  --model gpt-5.4                  \
  --reasoning-effort medium
```

If generation fails (parse error, compile error), FastDyn automatically retries with the error appended to the prompt, up to a configurable number of attempts.

LLM prompt/response pairs are saved permanently in `fastdyn_llm_history/` (sibling of `fastdyn_work`) as `NNN_prompt.txt` / `NNN_response_M.txt`, accumulating across runs for debugging and audit.

---

### Step 3 — Run the firmware with the learned model

Update the platform config (`.toml`) to set the relevant devices to `elder` backend pointing at the compiled `.so`. Then rerun:

```bash
fastdyn run -c <config.toml>
```

Output: `io.log` (emulation trace)

---

### Step 4 — Verify against the hardware trace

The Verifier replays `hardware_log/io.log` through the emulated model and compares responses register by register.

```bash
fastdyn verifier \
  -hw hardware_log/io.log    \   # ground-truth hardware trace
  -em io.log                 \   # emulation trace from Step 3
  -b <platform>              \
  -p <PERIPH1> [-p ...]      \   # peripherals to check
  -mname <ModelName>         \   # logical model name (repeatable)
  -d <ModelName>:path/to/model.c \  # source file for each model (repeatable)
```

The Verifier reports:
- **Entropy mismatches** — registers where value variability differs between hardware and emulation (data-bearing registers expected to differ are flagged as warnings, not errors)
- **Behavioral mismatches** — control register values that diverge from the hardware trace
- **ISR mismatches** — interrupt handlers fired in hardware but not in emulation, or vice versa

If mismatches are found, a unified `fastdyn_work/revised_prompt.txt` is written describing each issue with the current model source included for context.

---

### Step 4a — Apply LLM correction patches (RCA loop)

Send `revised_prompt.txt` back to the LLM. It responds with SEARCH/REPLACE patches that are applied atomically to the model files and recompiled.

```bash
fastdyn llm \
  -d fastdyn_work \
  -o path/to/model1.c \
  [-o path/to/model2.c ...] \
  --compile \
  --model gpt-5.4 --reasoning-effort medium \
  --stateless
```

Repeat Steps 3 → 4 → 4a until the Verifier reports no mismatches. In practice, simple peripherals (GPIO, UART, timers, PWM) converge in under 3 iterations. Complex peripherals (I²C, SPI, ADC+DMA) typically need 4–7 iterations.

## Compositional Modeling

BoardRunner decomposes the rehosting problem into per-peripheral subproblems. Instead of one monolithic platform model, each peripheral (or tightly coupled group) gets its own `.so` model. This is the core design principle that makes BoardRunner scalable.

**Inter-model communication** uses the signals API:

```c
// Publisher (e.g. GPIOC model):
api_signal_set(signal_id, level);

// Subscriber (e.g. EXTI model):
api_signal_register(signal_id, handler_fn, opaque);
```

The signal ID convention follows the peripheral's natural numbering (e.g., signal 13 = EXTI line 13 = PC13). This lets models communicate without knowing each other's internal state.

Peripherals that are not being modeled (e.g., SYSCFG, output GPIO, RCC) are left in **passthrough** mode and continue to reach real hardware. This is intentional — it keeps the scope of each model small and avoids disturbing peripherals that are already working correctly on hardware.

## Platform Configuration (.toml)

Each example has a `.toml` file that tells FastDyn how to route MMIO for every address range. Example structure:

```toml
[Device.my_peripheral]
    ranges = [["0x40020000", "0x400203FF"]]
    read_priority = "elder"

    [[Device.my_peripheral.handlers]]
        model   = "elder"
        enabled = true
        scroll  = "boardrunner/boardrunner_sdk/build/model.so"

    [[Device.my_peripheral.handlers]]
        model   = "passthrough"
        enabled = false

[Device.remaining_space]
    ranges = [["0x40000000", "0xDFFFFFFF"]]   # everything else

    [[Device.remaining_space.handlers]]
        model   = "passthrough"
        enabled = true
```

Switch `enabled = true/false` on the handlers to change which backend handles a peripheral without editing any other file.

## Key FastDyn CLI Commands

| Command | Purpose |
|---------|---------|
| `fastdyn run -c <toml>` | Run firmware (passthrough, elder, or hybrid) |
| `fastdyn generate ...` | Encode I/O trace and generate LLM prompt |
| `fastdyn llm -d <work> -o <model.c> ...` | Send prompt to LLM, write and compile model |
| `fastdyn verifier ...` | Diff emulation vs. hardware trace, produce correction prompt |

Full option reference: `src/fastdyn/main.py` or `fastdyn <command> --help`.
