### 1. Previous Model Failure Analysis
The mismatch is caused by the model incorrectly tying RX availability to TX activity: every write to `FIFO` immediately injects a receive byte, so the next `STATUS` read becomes `0x140`. The hardware trace shows the opposite behavior: after repeated TX writes, `STATUS` usually stays `0x50`, and only rarely transitions to `0x140` when asynchronous RX data actually arrives. The current model already had the right basic idea with a timer-based RX path, but that timer was never armed, so a later workaround introduced the incorrect TX-triggered RX behavior. The fix is to make RX arrival asynchronous again: start the scripted RX stream when the UART reaches its ready/active configuration, inject bytes via timer, and never inject RX data directly from TX FIFO writes.

### 2. Register Analysis
- **`CTRL` @ `0x00`**
  - Main control/configuration register.
  - Firmware performs read-modify-write sequences on it.
  - `0x00000001` appears to be the UART enable bit.
  - `0x00008000` appears to be part of the “fully active” configuration.
  - `0x00080000` is read-only/status-like: after writing `0x28C01`, hardware reads back `0xA8C01`.

- **`STATUS` @ `0x04`**
  - Polled status register.
  - `0x50` is the normal idle/TX-ready state.
  - `0x140` indicates RX data available.
  - Hardware does **not** switch to `0x140` immediately after TX writes; RX-ready is asynchronous.

- **`CLKDIV` @ `0x10`**
  - Baud-rate divider/config register.
  - Written with `0x40` during initialization.

- **`OSR` @ `0x14`**
  - Oversampling configuration register.
  - Written with `0x5` during initialization.

- **`FIFO` @ `0x20`**
  - TX data register on write.
  - RX data register on read.
  - Hardware RX sequence returns `"Hello"` (`0x48 0x65 0x6C 0x6C 0x6F`).

    if (s == NULL) {
        return;

    s->rx_timer_armed = false;

        return;
    }

    if (s->rx_script_pos >= sizeof(g_uart_rx_script)) {
        return;
