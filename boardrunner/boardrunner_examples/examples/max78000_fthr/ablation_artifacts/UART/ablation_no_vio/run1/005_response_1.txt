### 1. Previous Model Failure Analysis
The mismatch comes from the model treating `STATUS` RX-ready (`0x140`) as a level derived directly from RX FIFO occupancy and starting the scripted RX stream as soon as the UART becomes ready during init. In the hardware trace, `STATUS` is almost always the idle/TX-ready value `0x50`, with `0x140` appearing only briefly just before firmware reads a received byte. That means the current model exposes RX-ready too early and for too long. The fix is to make RX indication a transient latched status event, not a permanent reflection of unread FIFO data, and to begin the scripted receive stream during runtime TX activity rather than immediately at enable time.

### 2. Register Analysis
- **`CTRL` @ `0x40042000`**
  - Main control/configuration register.
  - Firmware performs RMW on it during init.
  - Bit `0x1` behaves like UART enable.
  - Bit `0x8000` participates in the “fully active” config written before the final ready state.
  - Bit `0x80000` is read-only/latched on reads after final activation: write `0x28C01`, read back `0xA8C01`.

- **`STATUS` @ `0x40042004`**
  - Polled during runtime.
  - Dominant idle/TX-ready value is `0x50`.
  - Rare RX-available indication is `0x140`, seen immediately before firmware reads `FIFO`.
  - Therefore RX indication should be brief/transient, not continuously asserted while FIFO holds unread data.

- **`CLKDIV` @ `0x40042010`**
  - Baud/clock divider register.
  - Firmware writes `0x40` during initialization.

- **`OSR` @ `0x40042014`**
  - Oversampling register.
  - Firmware writes `0x5` during initialization.

- **`FIFO` @ `0x40042020`**
  - TX data register on write.
  - RX data register on read.
  - Observed RX byte sequence is `"Hello"` (`0x48 0x65 0x6C 0x6C 0x6F`).
