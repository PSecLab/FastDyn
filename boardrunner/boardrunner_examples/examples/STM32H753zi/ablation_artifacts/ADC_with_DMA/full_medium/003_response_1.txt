### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause 1:** `ADC->CFGR` currently echoes back all written bits, but the hardware trace shows bit `0x00200000` does **not** read back. That makes `CFGR` entropy too high and shifts firmware control flow during ADC setup.
  - **Root cause 2:** The ADC model is issuing DMA requests on logical ID `1`, but the trace shows `DMAMUX1_C1CR = 0x9`, so ADC1 should be requesting **DMAMUX request ID 9**, not direct stream ID 1.
  - **Root cause 3:** The DMA model’s “direct stream fallback” is too permissive. It can service ID `1` directly on Stream 1 even when DMAMUX channel 1 is explicitly configured for request ID 9. That can create spurious transfers/errors and explains the DMA-side symptom (`LISR=0x200` instead of `0xC00`).
  - **Bug file(s):**
    - `ADC/model.c`
    - `DMA_with_DMAMUX1/model2.c`
  - **Risk to passing peripherals:** Low.
    - `ADC12_Common` is separate and should not regress.
    - `DMAMUX1` register behavior is unchanged; only request routing behavior is tightened to respect configured DMAMUX channels.

- **ADC2**
  - **Root cause:** No independent ADC2-only bug is strongly evidenced. Its mismatch is most likely a **secondary divergence** from the shared ADC model / DMA flow: once ADC1 setup and DMA interrupt behavior diverge, firmware execution order changes and ADC2’s expected CR transition is not reached in the same way.
  - **Bug file(s):**
    - `ADC/model.c`
  - **Risk to passing peripherals:** Low; this is a shared ADC behavioral correction, not an ADC2-specific special case.

- **DMA1**
  - **Root cause:** DMA request routing is wrong at the system level:
    - ADC1 is using the wrong DMA request ID.
    - DMA fallback routing ignores active DMAMUX configuration and can service the wrong logical ID directly.
  - **Manifestation:** `LISR` shows `0x200` (TE) in emulation instead of hardware’s `0xC00` (HT+TC), and the DMA IRQ path never matches.
  - **Bug file(s):**
    - `ADC/model.c`
    - `DMA_with_DMAMUX1/model2.c`
  - **Risk to passing peripherals:** Low; the DMA change only disables direct-ID fallback when that stream’s DMAMUX channel is already configured.

### 2. Register Analysis

- **ADC1/ADC2 `CR`**
  - Command/power-control register.
  - Low command bits like `ADEN/ADDIS/ADSTART/ADSTP/ADCAL` are one-shot/self-clearing.
  - High power bits such as `DEEPPWD` / `ADVREGEN` are persistent software-visible state.

- **ADC1 `CFGR`**
  - Main regular-conversion configuration register.
  - Trace-backed writable/read-back bits are only the observed ones: `0x80000000`, `0x00003000`, `0x00000003`.
  - Bit `0x00200000` is written by firmware but does not read back in hardware trace, so it must be masked out.

- **ADC1 `ISR`**
  - Status register with sticky hardware flags.
  - Observed values imply use of:
    - `ADRDY`
    - `EOSMP`
    - `EOS`
    - `CFGRDY`

- **DMA1 `S1CR`**
  - Stream 1 configuration / enable register.
  - Trace shows normal progression to `0x12D1F`; the model’s main issue is not S1CR storage but incorrect request servicing.

- **DMA1 `LISR` / `LIFCR`**
  - Stream status and clear registers.
  - Hardware shows Stream 1 `HTIF1|TCIF1 = 0xC00`.
  - Firmware clears them independently with `0x400` then `0x800`.

- **DMAMUX1 `C1CR`**
  - Channel 1 request selection.
  - `0x9` is the key trace fact: DMA1 Stream 1 is connected to **request ID 9**, so producers must call DMA API with ID 9.

- **ADC1 `DR`**
  - Data register is the effective source of DMA payload.
  - In this framework, the ADC model should inject payload bytes through `api_dma_request_data()` rather than relying on DMA to read MMIO.
