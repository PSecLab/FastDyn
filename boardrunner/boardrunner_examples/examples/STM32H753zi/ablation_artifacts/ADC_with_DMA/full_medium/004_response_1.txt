### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** The dominant failure is in the **DMA model**, not ADC1’s own conversion logic. ADC1 is correctly configured to use DMAMUX request ID `9`, routed through **DMAMUX1 C1CR=0x9** to **DMA1 Stream1**. But the current DMA payload path can latch **TEIF1** on peripheral-provided ADC samples instead of completing the transfer and setting **HTIF1/TCIF1**. That matches the observed `DMA1->LISR` mismatch: hardware shows `0xC00` (HT+TC), emulation shows `0x200` (TE).
  - **Bug file:** `DMA_with_DMAMUX1/model2.c`
  - **Secondary ADC-side issue:** The ADC model has an evidence-backed register map bug: `DIFSEL` and `CALFACT` offsets are wrong for STM32H753 ADC (`0xC0/0xC4`, not `0xB0/0xB4`). This is not the main cause of the DMA/IRQ failure, but it is still a real ADC model bug.
  - **Bug file:** `ADC/model.c`
  - **Regression risk:** Low. The DMA fix only changes payload-backed P2M completion behavior; DMAMUX1 register behavior is untouched. The ADC register-offset fix only affects ADC tail registers and does not touch `ADC12_Common`.

- **ADC2**
  - **Root cause:** The mismatch is local to the **ADC model**. The trace shows `ADC2->CR` changing, while the model keeps returning `0x0`. The only evidence-backed ADC-model bug in the supplied code is the incorrect tail-register map (`DIFSEL/CALFACT`). The `CR` high-bit behavior is already intended to be preserved in the current code, so the dominant actionable fix here is still within `ADC/model.c`.
  - **Bug file:** `ADC/model.c`
  - **Regression risk:** Low. The change is limited to correcting register offsets.

- **DMA1**
  - **Root cause:** The DMA model incorrectly turns ADC payload requests into **TE** instead of progressing the stream and generating the expected **HT/TC** flags/IRQ flow.
  - **Bug file:** `DMA_with_DMAMUX1/model2.c`
  - **Regression risk:** Low to moderate. It slightly relaxes transfer-error behavior only for the **payload-backed peripheral-to-memory path**, which is exactly the path used by ADC1 here. Passing `DMAMUX1` behavior should not regress.

---

### 2. Register Analysis

- **ADCx->CR**
  - Mixed register: low bits are command/self-clearing control bits; high bits are persistent power/config bits.
  - ADC2 mismatch shows firmware expects CR readback to change over time/init sequence.

- **ADC1->CFGR**
  - Holds DMA-related enable/config bits and continuous conversion mode.
  - Final hardware state `0x80003003` is what gates ADC1 DMA requests.

- **ADC1->ISR**
  - Hardware status register used by firmware to observe progression:
    - `ADRDY`
    - `CFGRDY`
    - `EOSMP`
    - `EOS`
  - ADC1 mismatch is mostly downstream of broken DMA interrupt flow.

- **ADCx->DIFSEL / CALFACT**
  - Tail registers in the ADC instance register map.
  - Current model uses wrong offsets; hardware accesses them at `0xC0/0xC4`.

- **DMA1->S1CR**
  - Stream1 configuration register.
  - Trace-backed stream used for ADC1 DMA.
  - Readback already largely matches; problem is not stream programming but transfer completion/flagging.

- **DMA1->LISR / LIFCR**
  - Hardware shows `HTIF1|TCIF1` (`0xC00`) for the ADC stream.
  - Emulation shows `TEIF1` (`0x200`), which is the main DMA mismatch.

- **DMAMUX1->C1CR**
  - Carries request ID `9`.
  - Confirms ADC1 should request DMA through DMAMUX request ID 9 and land on DMA1 Stream1.
  - Current routing logic is conceptually correct; the bug is in transfer servicing.
