### 1. Cross-Model Failure Analysis

- **ADC2 mismatch root cause**
  - The only observed mismatch is on **`ADC2->CR`**: hardware reads `0x0` first, then later `0x20000000`, while the model stays at `0x0`.
  - There is **no evidence this is caused by DMA/DMAMUX**. The failing register is internal ADC state, and ADC2 has no trace-backed DMA activity here.
  - The most plausible explanation is that **ADC2’s CR reset/deep-power-down state becomes visible later than the current model represents**. In real hardware this can happen because of ADC reset/power-state interactions outside the ADC MMIO stream; since we do not have an RCC/reset API in scope, the ADC model needs a local heuristic.

- **Bug location**
  - **File:** `ADC/model.c`

- **Regression risk**
  - **Low** if the fix is scoped to **ADC2 only**.
  - `ADC1`, `DMA1`, and `DMAMUX1` are passing and should not be touched unless necessary. No DMA model change is warranted.

---

### 2. Register Analysis

- **`ADC2->CR`**
  - Control register containing persistent power-state bits like **`DEEPPWD`** and **`ADVREGEN`**, plus self-clearing command bits.
  - The mismatch is specifically the visibility of **`DEEPPWD` (`0x20000000`)**.
  - Hardware shows `CR` transitioning from `0x0` to `0x20000000` without any trace-backed ADC2 MMIO write, so the model needs to expose that state change locally.
