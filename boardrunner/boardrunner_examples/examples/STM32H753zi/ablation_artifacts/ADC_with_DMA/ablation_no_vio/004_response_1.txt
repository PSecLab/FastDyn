### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** `ADC_CR` command bits are being modeled too much like normal latched register bits. In particular, `ADSTART` is only honored when the readable `CR` image still contains `ADEN`. But on STM32H7, firmware commonly writes command-only values to `CR`, and command bits are effectively one-shot actions rather than persistent readback state. As a result, the model often loses the internal enabled state before `ADSTART` is evaluated, so conversion never starts and `ISR` never transitions from `0x1001` to `0x100F/0x100B`.
  - **Bug location:** `ADC/model.c`
  - **Regression risk:** Low. The fix is confined to per-ADC `CR` semantics and should not affect `ADC12_Common`. DMA/DMAMUX already match and do not appear to be the source of the ADC1 mismatch.

- **ADC2**
  - **Root cause:** Same `ADC_CR` modeling bug. The model conflates readable power/config bits with command bits, so command writes can incorrectly destroy visible `CR` state and prevent the expected `0x20000000` readback transition.
  - **Bug location:** `ADC/model.c`
  - **Regression risk:** Low. This is the same fix as ADC1 and should improve consistency for both ADC instances without touching passing DMA/DMAMUX behavior.

- **Why not DMA_with_DMAMUX1?**
  - DMA1 and DMAMUX1 are already passing, including stream state and ISR timing patterns. The observed failing value is specifically `ADC1->ISR`, not a DMA flag or transfer register. So the root cause is in ADC state generation, not in DMA request routing.

---

### 2. Register Analysis

- **ADCx_CR**
  - Mixes:
    - **Readable/persistent power/config bits**: notably `ADVREGEN`, `DEEPPWD` and possibly `ADCALDIF`
    - **One-shot command bits**: `ADEN`, `ADDIS`, `ADSTART`, `JADSTART`, `ADSTP`, `JADSTP`, `ADCAL`
  - The trace implies command writes must affect internal state without requiring those bits to remain readable in `CR`.

- **ADCx_ISR**
  - `ADRDY` and `LDORDY` are already modeled and visible as `0x1001`.
  - Missing transition is the regular-conversion status behavior:
    - one rare `0x100F` read
    - then stable `0x100B`
  - This implies conversion start should set `EOSMP | EOS | EOC`, and `EOC` should self-clear after one read in this simplified model.

- **ADCx_CFGR**
  - Already matches.
  - Included in loop patterns because firmware checks mode/config while polling status, but it is not the root cause.
