### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** in `ADC/model.c`
    - `ADC_ISR.EOC` is asserted too early: the current model makes `EOC` appear on the first ISR read after `ADSTART`, but hardware mostly shows `ISR=0x100B` (`ADRDY|EOSMP|EOS`) and only rarely `0x100F`.
    - `ADC_CR` visible power bits (`DEEPPWD`, `ADVREGEN`) are applied with immediate readback. The trace shows at least a **one-read lag** before the new visible CR state becomes observable, which explains both the CR entropy mismatch and the off-by-one readback timing.
  - **Bug file:** `ADC/model.c`
  - **Regression risk:** low if scoped to ADC CR readback timing and delayed EOC pulse generation. `ADC12_Common` is separate in the same file but currently passing; changes below do not touch common-register behavior.

- **ADC2**
  - **Root cause:** same `ADC/model.c` CR readback timing bug.
    - Hardware shows `CR` transition `0x0 -> 0x20000000`, while emulation stays at `0x0`. This is consistent with the model missing deferred visibility of power bits or not reflecting the intended visible state on subsequent reads.
  - **Bug file:** `ADC/model.c`
  - **Regression risk:** low; this is the same CR visible-bit timing fix as for ADC1.

- **DMA / DMAMUX**
  - No strong evidence the DMA model is the root cause here.
  - `DMA1` and `DMAMUX1` are currently passing, and the ADC mismatches are directly explained by ADC register semantics, so changing `DMA_with_DMAMUX1/model2.c` would be unnecessary risk.

---

### 2. Register Analysis

- **ADCx_CR**
  - Readable power/config bits in this trace are mainly:
    - `DEEPPWD` bit 29
    - `ADVREGEN` bit 28
  - Command bits (`ADCAL`, `ADSTART`, `JADSTART`) are transient/polled and should not latch like normal RW bits.
  - Trace implies visible power-bit readback is **not immediate**; hardware exposes the old value for one more read before the new state appears.

- **ADCx_ISR**
  - `ADRDY` and `LDORDY` are sticky status bits in this workload.
  - During active regular conversion flow, hardware repeatedly shows:
    - `EOSMP` bit 1
    - `EOS` bit 3
  - `EOC` bit 2 is **rare**, not immediate on conversion start.

- **ADCx_CFGR**
  - Already behaves correctly for this trace.
  - `DMAEN/DMACFG`-like low bits are set in the dominant loop (`0x...0003`), consistent with DMA-backed conversions.
  - Bit 21 already correctly modeled as not sticking.
