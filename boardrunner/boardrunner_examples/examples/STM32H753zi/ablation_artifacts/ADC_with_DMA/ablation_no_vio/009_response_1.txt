### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** `ADC` model delays readback of writable `CR` power/config bits by one extra read. The firmware polls `CR` during ADC bring-up/calibration sequencing; with the delayed readback it gets stuck early and never reaches the later `CFGR`/`ISR` steady-state seen on hardware.
  - **Bug location:** `ADC/model.c`
  - **Regression risk:** Low. The change only removes a synthetic lag that is contradicted by the trace and keeps the existing transient handling for `ADCAL`, `ADSTART`, and `JADSTART`.

- **ADC2**
  - **Root cause:** Collateral divergence from the same ADC composite model bug. ADC2 shares the same `CR` logic, so once ADC1 init diverges, later ADC2 accesses no longer line up.
  - **Bug location:** `ADC/model.c`
  - **Regression risk:** Low, same reason as ADC1.

- **ADC12_Common**
  - **Root cause:** Also collateral. `CCR` storage is already basically fine, but execution never reaches the same point because ADC init diverges earlier on `CR`.
  - **Bug location:** Primary bug is still in `ADC/model.c`
  - **Regression risk:** Low.

- **DMA1**
  - **Root cause:** Two layers:
    1. **Primary trace divergence** is caused by the ADC model getting stuck before the firmware reaches the same DMA runtime path.
    2. **Secondary robustness bug** in the DMA model: first transfer completion depends on timer progress, but the framework warns that tight MMIO polling may not let the timer fire soon enough. That can suppress the expected `LISR=0xC00` and IRQ path.
  - **Bug location:** Primary in `ADC/model.c`, secondary robustness fix in `DMA_with_DMAMUX1/model2.c`
  - **Regression risk:** Low to moderate. The DMA fix is narrowly scoped to the first `LISR`/`S1CR` poll while stream 1 is active and no completion has happened yet.

- **DMAMUX1**
  - **Root cause:** Mostly collateral from earlier divergence. The `C1CR` storage path is already reasonable.
  - **Bug location:** No dedicated DMAMUX register-layout bug required; runtime alignment improves once ADC/DMA behavior is corrected.
  - **Regression risk:** Low.

---

### 2. Register Analysis

- **ADC1/ADC2 `CR`**
  - Firmware-polled control register.
  - Needs immediate readback for writable visible power/config bits.
  - Still needs transient/self-clearing behavior for command bits like `ADCAL`, `ADSTART`, `JADSTART`.

- **ADC1 `CFGR`**
  - Purely stateful configuration in this trace.
  - Hardware reaches `0x80000000`, then `0x80003000`, then `0x80003003`.
  - Current mismatches are secondary to being stuck before those writes complete.

- **ADC1 `ISR`**
  - Hardware shows `0x1001`, then `0x100B`, later `0x100F`.
  - Existing model already approximates this with `ADRDY`, `LDORDY`, `EOSMP`, `EOS`, delayed `EOC`; it just wasn’t being reached.

- **ADC12_Common `CCR`**
  - RMW’d by firmware; hardware eventually reads back `0x40000`.
  - Generic RW storage is sufficient once execution reaches it.

- **DMA1 `S1CR`**
  - Stateful config register; hardware reads progress through `0x12D00`, `0x12D16`, `0x12D1E`, `0x12D1F`.
  - Model storage is fine; the missing runtime path is mostly due to earlier divergence.

- **DMA1 `LISR` / `LIFCR`**
  - Hardware repeatedly sees `LISR=0xC00` and clears flags via `LIFCR`.
  - Model already sets/clears the right bits, but first completion may not happen if timer-based scheduling misses a tight poll loop.

- **DMAMUX1 `C1CR`**
  - Readback of configured request ID (`0x9` in the trace).
  - Existing storage behavior is acceptable.
