### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** `ADC/model.c` mishandles `ADC_CR`.
    - Readable CR bits (`ADVREGEN`/power-state bits) are applied with an artificial deferred update, so firmware sees stale values for extra polls.
    - `ADSTART`/`JADSTART` are modeled as permanently asserted via `regular_active`/`injected_active`, instead of transient hardware-owned status bits.
    - This can trap firmware in CR polling and prevent it from reaching later ADC, DMA, and common-register setup.
  - **Buggy file:** `ADC/model.c`
  - **Regression risk:** Low to moderate, limited to ADC1/ADC2/common ADC behavior. The change makes CR semantics *less sticky* and closer to hardware.

- **ADC2**
  - **Root cause:** Same shared ADC core bug in `ADC/model.c`.
    - ADC2 uses the same `ADCUnitState`/CR logic.
    - The missing `0x20000000` readback transition is consistent with broken CR visibility timing.
  - **Buggy file:** `ADC/model.c`
  - **Regression risk:** Low; same shared fix.

- **ADC12_Common**
  - **Root cause:** Mostly collateral damage from ADC1 bring-up stalling before firmware reaches the later `CCR` writes/reads.
    - The common-register model itself is simple RW storage and is likely sufficient once ADC CR polling progresses correctly.
  - **Buggy file:** `ADC/model.c`
  - **Regression risk:** Low.

- **DMA1**
  - **Root cause:** Primarily secondary fallout from ADC initialization not progressing to the expected DMA configuration/enable path.
    - Current DMA model already stores `S1CR`, `S1FCR`, `LISR`, and has a plausible IRQ/timer path.
    - The trace shows emulation never reaching the nonzero `S1CR` states seen on hardware.
  - **Buggy file:** Root cause is upstream in `ADC/model.c`, not clearly in `DMA_with_DMAMUX1/model2.c`.
  - **Regression risk if left unchanged:** None from the ADC fix; changing DMA now would be speculative.

- **DMAMUX1**
  - **Root cause:** Also collateral from the stalled bring-up path.
    - The model already supports `C1CR` storage and readback.
    - Missing `C1CR=0x9` is best explained by firmware not reaching that point.
  - **Buggy file:** Upstream `ADC/model.c`
  - **Regression risk:** None from ADC-only fix.

### 2. Register Analysis

- **ADC1/ADC2 `CR`**
  - Mixed register: readable power/config bits plus write-only / hardware-owned command-status bits.
  - `ADCAL` should self-clear after a short poll window.
  - `ADSTART` / `JADSTART` should be transient on reads, not permanently mirrored from software state.
  - Power-state visible bits must read back promptly after writes.

- **ADC1 `ISR`**
  - `ADRDY` and `LDORDY` are sticky hardware status bits after enable/regulator setup.
  - `EOSMP`/`EOS` are observed during the regular conversion flow.
  - `EOC` appears as an infrequent transient (`0x100F` rare vs dominant `0x100B`), so a one-shot model is appropriate.

- **ADC1 `CFGR`**
  - Mostly ordinary RW configuration storage.
  - Bit 21 appears non-sticky in trace and should remain ignored.
  - Divergence here was likely downstream of the CR polling problem, not CFGR itself.

- **ADC12_Common `CCR`**
  - Plain RW config register in observed trace.
  - Existing generic storage is adequate.

- **DMA1 `S1CR`**
  - Expected to progress through software-programmed configuration states and finally set `EN`.
  - Since emulation only saw zeros, this looks like firmware never reached the setup sequence.

- **DMA1 `LISR` / `LIFCR`**
  - `LISR` should expose `HTIF1|TCIF1` (`0xC00`) during the DMA-complete IRQ path.
  - `LIFCR` is W1C clearing of those flags.
  - Current DMA model already approximates this.

- **DMAMUX1 `C1CR`**
  - Simple channel request-selection/config storage.
  - Observed hardware value `0x9` is consistent with a normal request ID selection and should read back once firmware reaches it.
