### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** Two issues contribute:
    1. **ADC model bug** in `ADC/model.c`: `ADC_CR` power-state handling is too literal and likely misinterprets bit 29 semantics. The model currently treats bit 29 as destructive deep-power-down, clears state on it, and only raises `LDORDY` for bit 28. The trace shows `CR` transitioning through `0x20000000` and later `0x10000000`; treating bit 29 as destructive can stall init.
    2. **DMA model bug** in `DMA_with_DMAMUX1/model2.c`: DMA completion/IRQ happens too late (or never relative to firmware flow), so the firmware never reaches the ADC runtime ISR path where the dominant `ADC1->ISR` / `CFGR` reads occur.
  - **Bug file(s):** `model.c` and `model2.c`
  - **Regression risk:** Low if scoped to ADC12 CR power/calibration semantics and DMA1 stream1/channel1 startup timing only.

- **ADC2**
  - **Root cause:** Secondary control-flow divergence from ADC/DMA behavior. The `ADC2->CR` mismatch is consistent with the same ADC CR power-field issue; once ADC init/runtime flow matches, ADC2 access sequence should align better.
  - **Bug file(s):** primarily `model.c`
  - **Regression risk:** Low; change is shared CR behavior for ADC1/ADC2 and is conservative.

- **ADC12_Common**
  - **Root cause:** Mostly secondary divergence. The common `CCR` register model is already generic RW and should hold `0x40000` if firmware reaches that write. Missing runtime accesses are likely because earlier ADC/DMA flow diverges.
  - **Bug file(s):** no dedicated CCR bug evident; fallout from `model.c` / `model2.c`
  - **Regression risk:** None from leaving CCR logic as-is.

- **DMA1**
  - **Root cause:** `DMA_with_DMAMUX1/model2.c` delays the first transfer too much. The firmware expects stream1 activity/IRQ soon after stream enable; without it, `LISR` never becomes `0xC00` and the DMA ISR never runs.
  - **Bug file(s):** `model2.c`
  - **Regression risk:** Low if only the **first** stream1 event is accelerated, while later circular events keep the existing longer period.

- **DMAMUX1**
  - **Root cause:** No direct register-decoding bug is evident. Missing `C1CR` readback is a symptom of earlier divergence. However, stream1 activation logic in DMA depends on DMAMUX channel1, so fixing DMA startup timing is necessary for DMAMUX-visible behavior to line up.
  - **Bug file(s):** `model2.c`
  - **Regression risk:** Low; changes remain stream1/channel1-specific.

---

### 2. Register Analysis

- **ADC1/ADC2 `CR`**
  - Used for ADC power-up / regulator sequencing and calibration/start commands.
  - Trace implies:
    - visible power bits around `0x20000000` and `0x10000000`
    - command bits like `ADCAL` need transient readable behavior and self-clear
  - Current model is too destructive for bit 29 and too static for calibration visibility.

- **ADC1 `ISR`**
  - `0x1001`, `0x100B`, `0x100F` indicate `LDORDY`, `ADRDY`, and conversion-state bits.
  - `LDORDY` must become set during regulator/power sequencing.

- **ADC1 `CFGR`**
  - Generic RW behavior is mostly fine; missing later values are likely because firmware never reaches those writes/readbacks after divergence.

- **ADC12_Common `CCR`**
  - RMW register; value `0x40000` is software-written common ADC config.
  - Existing generic RW storage is sufficient if execution reaches it.

- **DMA1 `S1CR`**
  - Software config progresses through `0x12D00 -> 0x12D16 -> 0x12D1E -> 0x12D1F`.
  - Current model would store this correctly if flow reached it; the key missing piece is the subsequent DMA event/IRQ.

- **DMA1 `LISR` / `LIFCR`**
  - Hardware shows `LISR = 0xC00` for stream1 HT/TC.
  - Firmware clears flags via `LIFCR` in ISR.
  - Model already sets `0xC00` on completion, but completion is not happening soon enough.

- **DMAMUX1 `C1CR`**
  - Hardware readback `0x9` indicates request ID selection for DMA1 stream1.
  - Existing storage is adequate; the DMA startup path just needs to become active soon enough.
