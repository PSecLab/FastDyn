### 1. Cross-Model Failure Analysis

- **ADC1**
  - **Root cause:** in `ADC/model.c`
    - `CR` power/config bits were modeled as **immediately visible**, but hardware shows a **one-read delayed readback** for writes to the visible CR bits (`0x20000000`, `0x10000000` path). This explains the ADC1 `CR` entropy mismatch and also ADC2’s stuck loop.
    - `ISR` regular-conversion status progression is slightly wrong: hardware shows `ISR=0x1001` once, then quickly `0x100B`, while the model reaches `0x100B` too late in the observed loop. The model needs a short staged transition for `EOSMP/EOS`, and it should infer regular activity once the ADC is configured for DMA circular operation.
  - **Bug file:** `ADC/model.c`
  - **Regression risk:** low if kept narrow. `ADC12_Common` is separate state in the same file but untouched semantically. `DMA1`/`DMAMUX1` are already passing and do not need changes.

- **ADC2**
  - **Root cause:** same `CR` readback timing bug in `ADC/model.c`
    - Hardware shows `CR: 0x0 -> 0x20000000` on polling, but the model keeps returning `0x0`. This matches a missing **delayed visibility** behavior for the writable visible CR bits.
  - **Bug file:** `ADC/model.c`
  - **Regression risk:** low; this is the same fix as ADC1 and aligns both instances.

- **DMA_with_DMAMUX1**
  - No evidence the ADC mismatches come from DMA/DMAMUX. `DMA1` and `DMAMUX1` are passing and their observed sequences already line up.  
  - **No fix needed** in `model2.c`.

---

### 2. Register Analysis

- **ADCx_CR**
  - Readable subset is only the visible power/config bits plus transient command/status bits.
  - Hardware behavior inferred from trace:
    - writes to visible power bits (`0x20000000`, `0x10000000`) are **not reflected on the first read immediately after the write**
    - they become visible on the **next** poll
    - command bits like `ADCAL`, `ADSTART`, `JADSTART` remain transient/self-clearing in readback
  - This is the main source of the ADC2 mismatch and part of ADC1’s CR entropy mismatch.

- **ADC1_ISR**
  - Hardware-owned flags:
    - `LDORDY`/`ADRDY` are already mostly correct
    - `EOSMP|EOS` should appear **after a short transition**, not stay absent too long
    - `EOC` appears later as a rarer pulse (`0x100F`)
  - The trace suggests the ADC enters an active regular-conversion state once configured for DMA circular operation, even if explicit `ADSTART` isn’t the only observable trigger in the trace.

- **ADC1_CFGR**
  - Final observed active configuration is `0x80003003`
  - Low bits `0x3` strongly indicate DMA-enabled circular transfer configuration on this path
  - This is a reasonable minimal trigger to mark the ADC regular path active once the ADC is already enabled
